# Proposal: next steps for the Google Cloud source

Branch `improve/gcp-next`, started from `integration/all-threads`. Status: waiting for the owner.
Five goals, one commit each, plus a final commit with the docs.

## What changed

1. Notification channels. `importer convert-gcp-notifications --channels <export>/channels
   --alerts <converted run> --out <folder>`. Groups the converted conditions by their set of
   channels (one workflow to create per set), writes a shared-IR `NotificationPlan` per set and a
   report with the reason and manual steps for each channel type (email, token webhook, basic-auth
   webhook, Slack, PagerDuty; SMS, Pub/Sub, mobile and others have no New Relic destination).
   The condition-name lookup used by `convert-notifications` moved to
   `core/emit/notifications.py:converted_condition_names` and both commands call it.
2. Uptime checks. `importer convert-gcp-uptime --checks <export>/uptime-checks --out <folder>`.
   One row per check (path, period, New Relic run frequency that is not more often than Google's, the monitor to create) and
   the steps. The "uptime check alert" rule now points at it.
3. Dashboards. `DASHBOARD_REGISTRY["gcp"]`; `extract-gcp` also reads dashboards (v1 API, same
   allow-list). xyChart and scorecard widgets over a time series filter and text widgets convert;
   everything else is a "Not migrated" placeholder with a reason and steps. The metric, label and
   aggregation logic was extracted from the alert translator (`metric_series`, `check_aligner`)
   and used by both, so the alert output did not change (gate and golden unchanged).
4. Extractor hardening. New `core/safe_http.py`, used by the Google getter: status 300 or more is
   an error (no redirects), server text scrubbed of the token and `Bearer ...` and capped at 300
   characters, streamed 20 MB size cap, a total page cap of 200 across lists, and a token with
   non-ASCII characters or spaces is refused with a fixed message. Tested through
   `httpx.MockTransport` against the real getter.
5. `docs/research/count-null-empty-window.md`: where `count(*)` is emitted, what a change would
   touch, and a test plan. No emitter change.

## Risks

- Dashboards, channels and uptime checks were built from hand-made fixtures. No real export of
  any of them has been read, and the v1 dashboards list endpoint and its response shape are
  from memory of the API, not confirmed. Mosaic column count (48), field names and the
  `int64` strings are the same.
- The Google-side layout conversion (row heights, tile height halved) is a guess at a usable
  look, not matched to the console.
- Nothing is created in New Relic for channels or uptime checks. The export holds no addresses,
  URLs or secrets, by design, so the output is a to-do list with routing. The plan files use the
  shared IR with no destinations, so `apply-notifications` skips them.
- The New Relic run frequencies (1, 5, 10, 15, 30, 60 minutes), the claim that there is no TCP
  monitor, and the destination types named in the steps are from memory and not confirmed.
- Dashboard NRQL for counters sums the change per 5 minute window. It is not a rate, and the
  note says so. Metric names follow the same unconfirmed rule as alerts outside Compute Engine and
  Pub/Sub.
- Tightened extractor: a status of 300 or more is now an error. A Google endpoint that answers
  with a 3xx would have worked before and fails now.
- `access_token` now rejects an empty token from `gcloud` with the ASCII message, which is
  slightly misleading for that case.

## Owner decisions

1. Keep channel addresses out of the export (current), or allow an opt-in export that keeps them
   so `apply-notifications` can create destinations and disabled workflows for email and webhook.
   Secrets would still be manual.
2. Extend `improve-measure` to dashboards, channels and uptime checks so these goals show up in
   the rates and the gate protects them.
3. Run a live read of a real project's dashboards (read-only, no cost besides API calls) to check
   the response shape, then replace the hand-made fixtures with scrubbed real ones.
4. Whether to act on the `count(*)` note: run its live tests 1 and 4 first.
5. Whether `core/safe_http.py` replaces the Dynatrace copy (separate change; the other agent owns
   that package).

## Round 2 (reviewer findings)

Fixed on the same branch: names and paths that look like addresses, URLs or tokens are redacted in
the extractor and again in every planner and report (`core/redact.py`); uptime paths lose query
and fragment; dashboards place widgets without overlap (and say when they moved some), map stacked
bars to an area chart, keep distinct files for dashboards with the same long name, tolerate null
names, odd digits and a widget that raises; uptime periods that cannot be read give no frequency
and periods over 60 minutes are flagged; `safe_http` also scrubs URL-encoded tokens and
`Bearer:`, caps bytes across pages, has a run deadline, switches redirects off explicitly and
rejects a 200 that is not a JSON object; an empty token has its own message; reasons no longer
carry channel or widget text, so older broad rules cannot claim them; `convert-gcp-notifications`
refuses a non-empty `--out`. Gate: GATE PASSED, 940 tests passed.

Decisions for the owner: dashboard titles and display names are still copied as written (only
channel and uptime names are redacted); redaction errs towards hiding (a name with `=` or a
20-character mixed alphanumeric run is replaced, so some ordinary names will show as resource ids).
